1. Objetivos de la Auditoría

1.1 Objetivo General

Evaluar la efectividad, seguridad y alineación de los controles de tecnología de la información implementados en el sistema web comercial de Fusión Solar, con el fin de garantizar la confidencialidad, integridad y disponibilidad de la información transaccional (ventas, inventario, clientes y respaldos), así como el cumplimiento de las buenas prácticas de seguridad y de los estándares internacionales aplicables a una PyME del sector energético nicaragüense.

1.2 Objetivos Específicos

  1. Verificar el cumplimiento de las políticas internas de seguridad y de la normativa vigente en Nicaragua en materia de protección de datos personales y facturación electrónica.
  2. Evaluar los controles de acceso lógico implementados en la API (Django REST Framework) y en el frontend (React), prestando especial atención a la gestión de tokens, roles y privilegios administrativos.
  3. Revisar la eficacia del motor de respaldos en caliente y del protocolo pre_restore como mecanismo de recuperación ante desastres (DRP/BCP).
  4. Analizar la integridad y consistencia transaccional del Punto de Venta (POS), incluyendo el control de concurrencia mediante bloqueos pesimistas a nivel de base de datos.
  5. Verificar la trazabilidad de las operaciones críticas a través del módulo de auditoría global (AuditLog) implementado con Django Signals.
  6. Identificar vulnerabilidades técnicas, operativas y de infraestructura física en el módulo comercial de Altamira y en el servidor que aloja el sistema.
  7. Evaluar la continuidad operativa del sistema frente a fallos del stack tecnológico (Python, Django, base de datos).
  8. Emitir recomendaciones priorizadas que permitan a la gerencia de Fusión Solar tomar decisiones informadas y ejecutar un plan de acción correctiva a corto y mediano plazo.

2. Alcance

La auditoría abarcará los siguientes componentes dentro del período comprendido entre el 5 de octubre y el 6 de noviembre de 2026:

2.1 Sistemas y Aplicaciones

  • Backend: API REST desarrollada en Django REST Framework (endpoints de productos, clientes, ventas, compras, usuarios, respaldos y dashboard analítico).
  • Frontend: Aplicación web SPA desarrollada en React + Vite.
  • Base de Datos: SQLite en entorno de desarrollo (evaluación de factibilidad de migración a PostgreSQL).
  • Motor de Auditoría: Módulo AuditLog con Django Signals.
  • Módulo de Respaldos: Vistas /backups/create/, /backups/restore/ y protocolo pre_restore.

2.2 Infraestructura

  • Servidor(es) donde se aloja el sistema web (módulo Altamira).
  • Red local (LAN) del módulo comercial y conectividad a internet.
  • Equipos de punto de venta utilizados por los vendedores.
  • Dispositivos de almacenamiento de respaldos.

2.3 Procesos

  • Gestión de usuarios, roles y privilegios (IAM).
  • Administración de contraseñas y políticas de autenticación.
  • Gestión de cambios y despliegues en el sistema.
  • Copias de seguridad y procedimientos de restauración.
  • Registro y monitoreo de operaciones críticas (auditoría).
  • Manejo de información sensible de clientes (PII).

2.4 Exclusiones

Quedan fuera del alcance de esta auditoría:

  • Los equipos de instalación solar en campo (área técnica-operativa, no informática).
  • Los sistemas contables externos contratados a terceros.
  • La infraestructura de servicios en la nube de terceros (correo electrónico corporativo, si aplica).
  • Auditoría forense de incidentes previos no documentados.

8. Programa de Trabajo de Auditoría Detallado

El programa de trabajo establece los procedimientos de prueba, técnicas de muestreo e inspección de evidencias necesarias para verificar la efectividad de los controles asociados a los riesgos identificados. Se estructura en 6 módulos de trabajo alineados con los estándares ISO/IEC 27001 y NIST SP 800-53.

MÓDULO 1 — Control de Acceso Lógico y Gestión de Identidades (IAM)
Riesgos: R-01, R-02, R-10 · Estándares: ISO 27001 A.5.15–A.5.18 · NIST AC-2, AC-6

Objetivo: Evaluar la efectividad de los controles de acceso implementados en la API y verificar la correcta segregación de roles entre vendedores, administradores y usuarios inactivos.

Paso 1 — Inventario de endpoints y matriz de permisos

Procedimiento: Solicitar al Líder Técnico el listado completo de endpoints de la API REST (urls.py) e identificar para cada uno qué tipo de autenticación requiere.

Evidencia a recolectar: Copia del archivo urls.py, matriz de endpoints vs. permisos, capturas de las clases ViewSet y APIView.

Criterio de aceptación: El 100% de los endpoints que exponen datos sensibles debe requerir token de autenticación (IsAuthenticated) o privilegios de administrador (IsAdminUser).

Paso 2 — Pruebas de acceso anónimo (sin token)

Procedimiento: Ejecutar peticiones HTTP GET/POST a cada endpoint crítico sin enviar el header Authorization. Registrar el código de respuesta.

Evidencia a recolectar: Reporte del escáner OWASP ZAP, capturas de Postman/curl con las respuestas HTTP.

Criterio de aceptación: Todos los endpoints deben devolver HTTP 401 (Unauthorized) o 403 (Forbidden).

Paso 3 — Pruebas de escalada de privilegios

Procedimiento: Autenticarse con un usuario con is_staff=False e intentar: (a) listar todos los usuarios, (b) crear un usuario con is_staff=True, (c) acceder a la lista de respaldos.

Evidencia a recolectar: Capturas de las peticiones y respuestas HTTP, logs del servidor, reporte del test automatizado RoleBasedAccessControlTest.

Criterio de aceptación: Todas las acciones administrativas deben devolver HTTP 403 (Forbidden).

Paso 4 — Revisión del inventario de usuarios activos

Procedimiento: Extraer el listado completo de usuarios del sistema con campos username, is_staff, is_active, last_login y date_joined.

Evidencia a recolectar: Exportación en CSV del modelo User, capturas de la vista /employees del frontend.

Criterio de aceptación: No deben existir cuentas activas con más de 30 días sin inicio de sesión; solo cuentas con justificación de negocio deben tener is_staff=True.

MÓDULO 2 — Integridad Transaccional y Validación de Datos
Riesgos: R-07 · Estándares: ISO 27001 A.8.15–A.8.16 · NIST SI-10

Objetivo: Verificar la consistencia contable del POS y la robustez de los serializers frente a payloads maliciosos o erróneos.

Paso 1 — Pruebas de validación de serializers

Procedimiento: Enviar payloads inválidos a los endpoints de creación (productos, compras, ventas): campos faltantes, tipos incorrectos, valores negativos.

Evidencia a recolectar: Salida de la suite BackendSerializerValidationTest con Django TestCase.

Criterio de aceptación: El 100% de los payloads inválidos debe devolver HTTP 400 (Bad Request).

Paso 2 — Verificación de unicidad de comprobantes

Procedimiento: Intentar registrar la misma compra (mismo invoice_number + mismo proveedor) dos veces consecutivas.

Evidencia a recolectar: Salida del test DuplicatePurchaseRegressionTest, capturas de Postman.

Criterio de aceptación: El segundo intento debe devolver HTTP 400 con mensaje de factura duplicada.

Paso 3 — Verificación de integridad contable

Procedimiento: Registrar una venta con múltiples ítems y verificar que Sale.total_amount coincida exactamente con la suma de los SaleDetail.

Evidencia a recolectar: Salida del test SaleIntegrityRegressionTest.

Criterio de aceptación: Diferencia entre ambos valores debe ser 0.

MÓDULO 3 — Protección de Datos Sensibles y Respaldos
Riesgos: R-03, R-05 · Estándares: ISO 27001 A.8.24, A.5.29 · NIST SC-13, CP-9

Objetivo: Verificar la protección de contraseñas, datos personales de clientes (PII) y el ciclo completo de respaldo/restauración.

Paso 1 — Verificación de fortaleza de contraseñas

Procedimiento: Intentar cambiar la contraseña a valores débiles ("a", "123", "password") vía POST directo al endpoint de reset.

Evidencia a recolectar: Salida del test PasswordStrengthValidationTest.

Criterio de aceptación: El backend debe rechazar contraseñas que no cumplan el regex (8+ caracteres, 1 mayúscula, 1 minúscula, 1 número).

Paso 2 — Verificación del ciclo de respaldos

Procedimiento: Ejecutar el ciclo completo: crear backup → listar → descargar → restaurar (verificar pre_restore) → eliminar.

Evidencia a recolectar: Salida del test BackupLifecycleTest, capturas de la interfaz web (/backups), inspección del sistema de archivos.

Criterio de aceptación: Cada operación debe completarse sin errores, y el archivo pre_restore_*.db debe generarse automáticamente antes de cada restauración.

Paso 3 — Revisión de cifrado en reposo (si aplica)

Procedimiento: Verificar si la base de datos SQLite y los archivos de respaldo están cifrados en disco.

Evidencia a recolectar: Inspección del sistema de archivos del servidor, salida de file sobre los archivos .db.

Criterio de aceptación: Los archivos deben estar cifrados con AES-256 o equivalente, o bien encontrarse en una ubicación física protegida.

MÓDULO 4 — Continuidad Operativa y Stack Tecnológico
Riesgos: R-04, R-06, R-09 · Estándares: ISO 27001 A.5.29–A.5.30 · NIST CP-2, CP-9

Objetivo: Evaluar la resiliencia del sistema frente a fallos técnicos, cortes eléctricos y cambios del stack.

Paso 1 — Evaluación de compatibilidad del stack

Procedimiento: Verificar las versiones de Python, Django, Node.js y React instaladas; contrastar contra la matriz de compatibilidad oficial.

Evidencia a recolectar: Salida de python --version, pip freeze, node --version, package.json.

Criterio de aceptación: Todas las versiones deben pertenecer al rango oficialmente soportado.

Paso 2 — Prueba de concurrencia en base de datos

Procedimiento: Simular dos ventas simultáneas del último artículo en stock. Verificar que solo una tenga éxito.

Evidencia a recolectar: Salida del test ConcurrencySaleTest, consultas SQL de bloqueo.

Criterio de aceptación: El sistema debe impedir la sobreventa (1 venta con HTTP 201, 1 con HTTP 400).

Paso 3 — Inspección física del módulo Altamira

Procedimiento: Visitar el módulo, verificar el estado del servidor, UPS, router, cableado y control de acceso físico.

Evidencia a recolectar: Fotografías del espacio físico, checklist firmado, inventario de hardware.

Criterio de aceptación: El servidor debe estar en un gabinete con llave, protegido por UPS y en un espacio con control de acceso.

MÓDULO 5 — Trazabilidad y Registro de Auditoría (Logs)
Estándares: ISO 27001 A.8.15 · NIST AU-2, AU-3, AU-6

Objetivo: Verificar la efectividad del módulo AuditLog implementado con Django Signals.

Paso 1 — Cobertura de eventos auditados

Procedimiento: Revisar el archivo signals.py e identificar qué modelos generan registros de auditoría (CREATE, UPDATE, DELETE).

Evidencia a recolectar: Copia de signals.py, matriz de modelos vs. eventos auditados.

Criterio de aceptación: Todos los modelos sensibles (Product, Customer, Sale, PurchaseOrder, User) deben generar AuditLog.

Paso 2 — Captura del usuario ejecutor

Procedimiento: Verificar que los registros de AuditLog contengan el usuario autenticado (vía CurrentUserMiddleware).

Evidencia a recolectar: Salida del test AuditLogSignalTest, consultas SQL a la tabla AuditLog.

Criterio de aceptación: El campo user debe estar poblado con el usuario real, no NULL.

Paso 3 — Retención y protección de logs

Procedimiento: Verificar que los logs no puedan ser modificados ni eliminados por usuarios no autorizados.

Evidencia a recolectar: Permisos de la tabla en la base de datos, endpoints de acceso.

Criterio de aceptación: Solo usuarios con is_staff=True deben poder consultar la tabla de auditoría; nadie debe poder editarla.

MÓDULO 6 — Seguridad de la Aplicación Web (Frontend + API)
Estándares: OWASP Top 10 2021 · NIST SA-11

Objetivo: Verificar la ausencia de vulnerabilidades explotables en la aplicación web.

Paso 1 — Análisis de vulnerabilidades con OWASP ZAP

Procedimiento: Ejecutar escaneo pasivo y activo sobre el frontend (localhost:5173) y el backend (localhost:8000).

Evidencia a recolectar: Reportes HTML generados por ZAP, capturas de las alertas.

Criterio de aceptación: Cero (0) alertas de severidad Alta o Crítica.

Paso 2 — Pruebas de carga y rendimiento

Procedimiento: Ejecutar pruebas con k6 simulando 50 usuarios concurrentes sobre el Dashboard.

Evidencia a recolectar: Salida de k6, gráficos de tiempos de respuesta.

Criterio de aceptación: El p(90) de tiempo de respuesta debe ser inferior a 1500 ms.

Paso 3 — Revisión de cabeceras HTTP de seguridad

Procedimiento: Inspeccionar las cabeceras de respuesta del servidor y verificar presencia de: CSP, X-Frame-Options, X-Content-Type-Options, Permissions-Policy, Cross-Origin-*-Policy.

Evidencia a recolectar: Capturas del reporte ZAP, salida de curl -I.

Criterio de aceptación: Todas las cabeceras deben estar presentes con valores seguros.
